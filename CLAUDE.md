# iForget

Progressive Web App за бележки, изцяло на български. Живо на
**https://iforget.eu** (и стар адрес `neshovska.github.io/iforget/`, който
автоматично пренасочва, стандартно поведение на GitHub Pages при потвърден
custom domain).

Собственик/потребител: физическо лице, основно на iPhone/iPad. Комуникацията
за развитие на приложението е на български.

## Технически стек

- **Единствен файл `index.html`** (~2300 реда) — цялото приложение: HTML +
  `<style>` + `<script>`, без build стъпка, без npm зависимости за самото
  приложение.
- **Деплой:** GitHub Actions → GitHub Pages (workflow `static.yml`,
  тригър при push към `main`). Custom domain `iforget.eu` е свързан през
  `CNAME` файла + DNS записи в SuperHosting.
- **Firebase Auth** — вход само с имейл + парола (нарочно БЕЗ Google Sign-In,
  за да не се показва `firebaseapp.com` вместо `iforget.eu` при OAuth екран).
  Проект: `iforgetbg`.
- **Firestore** — облачно съхранение на бележките, `users/{uid}` документ на
  акаунт; security rules изискват `request.auth.uid == userId`.
- **localStorage** — локален кеш за мигновен старт/офлайн (`loadLocalCache()`
  преди Firebase да потвърди сесия), после презаписан от `loadFromCloud()`.
- **`reset-password.html`** — самостоятелна страница за забравена парола на
  `iforget.eu` домейна (вместо Firebase-овия hosted домейн); изисква ръчно
  "Customize action URL" в Firebase Console → Auth → Templates.

## Модел на данните

Бележка:
```
{ id, text, status: 'open'|'progress'|'done', createdAt, completedAt, tag, reminderAt, reminderRepeat: null|'daily'|'weekly', color: null|hex, subs: [] }
```
Подбележка: същата форма, но без собствен `tag` (само основните бележки имат
tag-picker в интерфейса).

Резервиран таг `deleted` = кошче (soft delete, виж по-долу) — не е обикновен
потребителски таг.

Firestore документ `users/{uid}` също съдържа `tagOrder: string[]` — редът на
потребителските тагове в реда с категории (виж `saveTagOrder()`), отделно
поле от `notes`, записва се само при разместване, не при всяка промяна на
бележка.

## Основни функции (към момента)

- **Статус на бележка** — кръгчето/dot превключва open ⇄ прогрес
  (тап отново маха "в прогрес" обратно на активна, `cycleStatus()`); НЕ
  слага "завършено" — то се задава единствено чрез swipe надясно
  (`markDoneBySwipe()`, сам управлява `completedAt`), по изрична заявка.
  **Обратният път — ДВА входа към `reopenItem()`:** (1) кръгчето върху
  приключена бележка (дотогава беше мъртъв бутон: натискаш и нищо не става,
  което изглежда като счупено, а не като забрана); (2) бутон в менюто при
  задържане, показван САМО върху приключена и САМО извън кошчето (в кошчето
  "връщане" значи връщане от Изтрити и двете едно до друго объркват).
  Асиметрията е нарочна: кръгчето може да ИЗВАДИ от "приключено", но никога
  да сложи там. Надписът на бутона е динамичен — "Върни в прогрес" или
  "Върни в активни" според `prevStatus`, за да казва КЪДЕ отива бележката.
  `markDoneBySwipe()` пази откъде идва бележката в `prevStatus`, за да се
  върне точно там — активна или "в прогрес", а не сляпо на активна. Пази се
  само ако още НЕ е приключена, иначе повторно плъзгане върху вече
  приключена би презаписало истинското предишно състояние със самото
  'done'. Бележки, приключени преди тази функция, нямат `prevStatus` и се
  връщат като активни (по-безопасното предположение).
  `reopenItem()` ЗАДЪЛЖИТЕЛНО трие и `completedAt`: по нея
  `archiveOldCompleted()` решава кога бележката отива в кошчето, а
  календарът/серията броят приключените за деня — остане ли, върнатата
  бележка пак ще бъде архивирана след 30 дни и ще се брои като приключена.
  Цветно кръгче + текстов статус до датата (само при прогрес/завършено,
  датата е винаги първа, статусът е веднага след нея). В главния списък
  (`render()`) само "Приключени" излизат в отделна секция най-горе, извън
  обичайния поток; "В прогрес" и активните (open) стоят ЗАЕДНО в един общ
  хронологичен поток, без разместване помежду им — само статус-точката на
  всяка бележка ги отличава визуално (за да не се "чупи" хронологията при
  смяна на статус на в-прогрес).
- **Подредба на картата (по подразбиране, "за дясна ръка")** — дата
  (+статус текст) горе в началото (вляво); кръгчето за статус вдясно, до
  края на текста; таг + "+ добави подбележка" + разгъни/скрий — накуп долу
  вдясно, в края на текста. Индентът на подбележките си остава вляво
  (непроменен), но кръгчето/датата вътре в тях са огледални както основната
  бележка. Оригиналната (преди-огледална) подредба е достъпна веднага чрез
  включване на "Режим за лявата ръка" в профила — вижте коментара над
  `.note-top`/`.note-main`/`.note .meta` в `<style>` за точните CSS
  стойности, ако потребителят поиска пълно връщане назад по подразбиране.
- **Подбележки** — "+ добави" в мета реда на основната бележка; визуално
  вложени с лява рамка-индикатор; малко по-голямо разстояние (16px) след
  цялата група преди следваща самостоятелна бележка (`.note-wrap:has(.subs)`).
  **Ред по статус** (`sortedSubs()`, използвана от `subsBlock()`) — активните
  (без статус) най-близо до основната бележка, "в прогрес" след тях,
  завършените — най-долу, по изрична заявка. САМО визуално подреждане:
  `note.subs` масивът НЕ се пипа/презаписва (`Array#sort` върху копие,
  `[...note.subs]`), значи не се вика `save()` заради самото подреждане —
  редът в паметта/облака си остава по реда на добавяне, само екранът го
  показва прегрупиран. Стабилно сортиране (гарантирано от ES2019) — подбе-
  лежки със същия статус пазят предишния си взаимен ред помежду си
  (обикновено реда на добавяне). Пресмята се на всеки `render()`, значи
  смяна на статус автоматично мести подбележката на новото ѝ място при
  следващото рисуване, без нищо специално да го задейства нарочно.
- **Тагове/категории** — вградени "Лични"/"Работни" + произволни
  потребителски тагове + скрит таг "Satori" (само за акаунт
  `neshovska@yahoo.com`, виж `SATORI_EMAIL`) + системен таг "Изтрити"
  (кошче). Филтър от бутона с категориите горе в topbar-а (`renderCatRow()`).
  Фиксиран, НЕразместваем ред в началото: Всички → В прогрес (бърз филтър
  по СТАТУС, не по таг — `PROGRESS_FILTER`, филтрира всички "в прогрес"
  бележки независимо от тага им; най-отпред сред истинските филтри, по
  изрична заявка) → Работни → Лични → Satori (ако е приложимо) → Изтрити
  (винаги видим, дори празно кошче — закачен като останалите, не се крие).
  След това потребителските тагове —
  тези МОГАТ да се разместват с дълго натискане (~480ms) + провлачване
  (`attachCatRowDrag()`), редът се пази в `tagOrder` (localStorage +
  Firestore `users/{uid}.tagOrder`, синхронизиран между устройства, виж
  `saveTagOrder()`/`orderedCustomTags()`).
  ВАЖНО за тъч устройства: обикновеният тап (филтриране) за потребителските
  тагове се обработва РЪЧНО на `pointerup` в `attachCatRowDrag()`, НЕ през
  нативния `click` — `touch-action:none` (нужен за самото провлачване) спира
  браузъра да синтезира `click` след допир на iOS Safari. CSS-ът за тези
  чипове има и `-webkit-touch-callout:none`/`-webkit-user-select:none`, за
  да не открадне iOS собствения си дълъг-натиск (callout/избор на текст)
  жеста преди нашия таймер.
- **Свиване/разгъване на реда с тагове, когато преливат над 2 реда** —
  `updateCatRowExpand()` мери `offsetTop` на чиповете (различни стойности =
  различни редове); ако станат >2 реда, редът се свива до 2
  (`.cat-row.collapsed`, `max-height` инлайн до долния край на 2-ри ред) и
  се показва кръгла стрелка (`#catRowMoreBtn`, `data-action="cat-row-toggle"`,
  в долния десен ъгъл, абсолютно позиционирана спрямо `.cat-row`) за пълно
  разгъване. Мери коректно дори докато редът вече Е свит (`overflow:hidden`
  не маха елементите от layout-а, само ги отрязва визуално). Преизмерва се
  при: всеки `renderCatRow()` (докато редът е отворен), отваряне на реда
  (`catBtn` click), тап на самата стрелка, и `resize` (broй-редове зависи от
  ширината на екрана).
  Бутонът `catBtn` в topbar-а: първо тапване отваря реда (свит); второ
  тапване (докато е отворен) го затваря И изчиства `categoryFilter` (връща
  на "Всички") — по изрична заявка, преди само затваряше без да чисти
  избрания филтър. `closeCatRow()` винаги нулира `catRowExpanded` на
  `false`, за да стартира свит следващия път (важи и когато редът се
  затваря автоматично заради отваряне на търсене/профил, не само от
  `catBtn`).
  При избор на потребителски таг (тап, `pointerup` в `attachCatRowDrag()`),
  ако редът преливаше над 2 реда в момента на избора, избраният таг се
  мести най-отпред сред потребителските (веднага след фиксираните — виж
  `tagOrder`/`orderedCustomTags()`, същия механизъм като ръчното
  разместване с провлачване) и редът автоматично се свива обратно до 2
  реда — за да остане видим избраният таг при следващо отваряне, без да
  заема голяма част от екрана. Ако таговете и без друго се събират в ≤2
  реда, нищо не се мести — само филтрира, както преди. Аналогична логика
  (само свиване, без местене — фиксираните чипове не са част от `tagOrder`)
  има и в делегирания `catRow` `click` слушател за фиксираните чипове.
- **Кошче (soft delete)** — изтрита бележка/подбележка получава таг
  `deleted` и виси 5 дни (`TRASH_RETENTION_MS`, чисти се с
  `purgeExpiredTrash()` при всяко зареждане), откриваема от филтъра
  "Изтрити" горе. Смяна на тага ѝ (тап върху тагчето) я връща обратно.
  Изтрита подбележка се "изважда" от родителя си като самостоятелна
  бележка в кошчето (данните не се губят, само вложеността).
- **Автоматично архивиране на приключените** (`archiveOldCompleted()`,
  `DONE_RETENTION_MS` = 30 дни) — приключена бележка, отметната преди повече
  от 30 дни, се мести в кошчето (не се трие направо, стои още 5 дни и може
  да се върне). Продуктова позиция: приложението е за "ден за ден", не
  архив. Но е и **техническа необходимост**: целият списък живее в ЕДИН
  документ във Firestore (`users/{uid}`, поле `notes`) и там таванът е
  твърд — 1 MB. При среден размер ~362 B на бележка това са ~2900 бележки;
  при 10 на ден таванът се удря за под година, а щом се удари, записът в
  облака започва да се проваля. Освен това при ВСЯКА промяна се презаписва
  целият документ, тоест старите бележки оскъпяват всяко отмятане.
  **Текущият календарен месец никога не се пипа**, независимо от давността —
  седмичната/месечната статистика в "Твоят преглед" брои по `createdAt` в
  текущия период и иначе би излязла грешна на границата на месеца.
  Върната от потребителя бележка получава `archiveExempt` (виж
  `setNoteTag()`), иначе следващото зареждане веднага би я архивирало пак и
  връщането би изглеждало счупено.
- **Дневно резюме** (`dayHistory`, ключ `dayHistory` в localStorage и във
  Firestore) — `{ 'ГГГГ-ММ-ДД': {c,d} }`, `c` = създадени, `d` = приключени
  през този ден. Пълни се в `purgeExpiredTrash()` в момента, в който
  бележка напусне масива ЗАВИНАГИ, и САМО за автоматично архивираните
  (`autoArchived`) — ръчно изтритите изчезват от статистиката както досега,
  защото потребителят ги е махнал съзнателно.
  Съществува, защото календарът брои по ДЕНЯ НА СЪЗДАВАНЕ
  (`calendarNotesCountForKey()`), а серията — по деня на ПРИКЛЮЧВАНЕ
  (`computeStreak()`); и двете четат резюмето наред с живите бележки. Без
  него чистенето би нулирало серията и би опразнило старите дни в календара.
  Проверено с Playwright: 90 поредни дни с по една приключена бележка →
  след архивиране и чистене остават 31 бележки, а серията си остава **90**;
  броячът в календара за стар ден е еднакъв преди и след чистенето.
  Цената е нищожна — ~27 B на ден (под 10 KB за година) срещу ~362 B на
  бележка.
  Потребителят Е уведомен за това на две места (данни, които изчезват сами,
  не бива да са само в кода): ред `.profile-hint` в профила → група "Данни"
  (стринг `retentionNote`) и отделна стъпка в обучението
  (`onboardStepCleanup`).
- **Обучение при първи вход** (`runOnboardingTour()`, `ONBOARD_TOTAL_STEPS`)
  — 8 стъпки: статус (дот) → таг → подбележка → swipe → long-press меню →
  вид на бележките (сочи `#userChip`, защото неонът/прозрачните се
  превключват от профила) → самопочистване на приключените → "пиши първата
  си бележка". Броят стъпки е в ЕДНА константа, а текстовете са
  `onboardStep*` ключове в петте езика — при добавяне на стъпка се пипат и
  двете, плюс `bigTarget` логиката (малките цели — дот/таг/текст/профилен
  бутон — понасят уголемяване при проблясване, целите карти не, виж
  коментара над `pulseHighlight()`).
  Показва се автоматично само при първи вход (`onboarded:true` във
  Firestore), но може да се пусне и ръчно от профила → "Помощ" → "Пусни
  обучението пак" (`data-action="replay-tutorial"`) — и за припомняне, и за
  тестване след промяна в стъпките, без нова регистрация. Бутонът затваря
  панела преди старта (иначе стои върху подсказките) и подава истинския
  `docRef`, за да се отбележи `onboarded:true` и ако първия път е било
  пропуснато. Безопасно е за данните: `finishOnboarding()` маха само
  демо бележката по id.
  Банерът за непотвърден имейл се СКРИВА, докато обучението тече
  (`onboardingActive` + `updateVerifyBanner()`), и се връща в
  `finishOnboarding()`. Реален проблем: при първи вход двете съвпадат по
  време по дефиниция (нов акаунт = непотвърден имейл + автоматично
  обучение), банерът стои най-горе и закрива подсказките. Напомнянето не е
  спешно и спокойно изчаква края.
  **Обучението остарява тихо — проверявай го при всяка нова функция.**
  Реален случай: "Цвят" и "Копирай" бяха добавени в long-press менюто, но
  `onboardStepCtx` (текстът) и `showOnboardCtxDemo()` (визуалната реплика на
  менюто) продължиха да изброяват само петте стари избора — обучението
  показваше меню, каквото потребителят после не вижда. `showOnboardCtxDemo()`
  Е реплика на `renderCtxMenuMain()` и ТРЯБВА да се пипа заедно с него.
- **Изписване на името: `iForget`** (малко "i", главно "F") — навсякъде,
  без изключение: интерфейс, заглавия, manifest, Capacitor конфигурация,
  Android/iOS ресурси, имейлите от Cloud Functions, документация. Малкото
  `iforget` в домейни/пакети/npm имена (`iforget.eu`, `iforget-capacitor`)
  си остава както е. Преди беше `IForget` — сменено по изрична заявка.
  **ВНИМАНИЕ:** имейлите (`functions/index.js` — възстановяване на парола,
  потвърждение на имейл, `FROM_EMAIL`) се променят само след повторен
  deploy на Cloud Functions; самата смяна в repo-то не стига.
- **Екран за вход — подредба на текстовете** (по изрична заявка): заглавие
  `iForget` → слоган `Think less. Do more.` (`authMotto`, СЪЩИЯТ на всички
  езици — марковата фраза не се превежда) → трите такта
  `Запиши. Направи. Приключи.` (`authBeats`, главни букви с разредка, за да
  се четат като стъпки, не като изречение) → три отметки `Твоите бележки /
  Твоят прогрес / Твоят контрол` (`authFeat1..3`) → формата → подпис
  `iForget — помни това, което има значение.` (`authSignature`).
  Подписът е НАЙ-ДОЛУ, под връзките за вход/регистрация — затваря
  страницата, вместо да прекъсва пътя към формата.
  Махнати при тази промяна: `authFeat4` (вече три отметки, не четири) и
  `authSubtitle` — беше дефиниран на петте езика, но НИКОГА не се е
  показвал никъде (мъртъв низ, открит при одита).
- **Чиста визия** (`CLEAN_LOOK_KEY`/`applyCleanLook()`, клас
  `html.clean-look`) — единствената БЕЗ фонова шарка: плътен цвят и нищо
  друго. За разлика от ученическата НЕ форсира светла тема — следва
  слънце/луна и има свой вариант за всяка.
  **Избира се от РЕДА С ЦВЕТОВЕТЕ в профила, не от бутон** (по изрична
  заявка) — кръгче `.color-sw.clean-sw`, двуцветно бяло/графит по модела на
  `.default-sw`, точно защото важи и за двете теми. Носи `data-look="clean"`
  вместо `data-color`; слушателят за цветовете затова селектира
  `.color-sw:not([data-look])` — иначе `profileColor` щеше да стане
  `undefined` при клик върху него.

  едновременно (`applyAccentColor()` пише inline на `:root` и бие класа).
  **Редът работи като ИЗБОР, не като ключове** (поправено по докладвано
  оплакване — двуцветно кръгче изглежда като избор на тема и потребителят
  очаква цъкането на друго да смени, а не да се налага повторен клик за
  гасене): повторен клик върху вече избраната чиста визия НЕ я маха
  (`if(cleanLook) return;`), а първото кръгче "по подразбиране" връща
  ОСНОВНИЯ ОБЛИК — маха и чистата, и ученическата визия, не само акцента.
  Затова и то свети само когато обликът наистина е основният
  (`profileColor === '' && !cleanLook && !schoolTheme`), а не просто когато
  няма избран цвят.
  Взаимно изключваща се с ученическата — иначе двата CSS блока се борят и
  резултатът зависи от реда им.

  `:root[data-theme="light"]`), затова светлият вариант е с добавен атрибут
  (0,3,0) и стои СЛЕД тъмния. Не разменяй двата блока.
- **Ученическа визия** (`SCHOOL_THEME_KEY`/`applySchoolTheme()`, клас
  `html.school-theme`, бутон в профила → "Изглед") — трета визия освен
  тъмната и светлата. **Живее в профилното меню, НЕ в горната лента** (по

  разбира, и напомнянията мълчат завинаги.

  се повтарят; чисти се на 30 дни. Приключените и изтритите се пропускат.

  приложението изсипва десетки стари напомняния наведнъж.

  **Баджът върху иконата — `clearDeliveredNativeNotifications()`.**
  Докладвано веднага след първия успешен тест: няма нито едно напомняне
  за днес, а иконата още показва червен бадж "1". Причина: `LN.cancel()`
  (в `syncNativeReminders()`) маха само НАСРОЧЕНИТЕ, още незвъннали
  известия. Звъннало веднъж, известието става "delivered" и живее в
  лентата на телефона, докато потребителят не го плъзне сам — нито
  приключването на бележката, нито изтриването ѝ го пипат, защото на
  това ниво то вече не е "напомняне", а обикновено известие. Баджът брои
  точно неизчистените известия в лентата.
  Решение (по изричен избор между двата варианта): `LN.
  removeAllDeliveredNotifications()` при СТАРТ и при ВРЪЩАНЕ към
  приложението (`visibilitychange`) — отваряш iForget, лентата и баджът
  се изчистват. Отхвърленият вариант беше "махай известието чак когато
  бележката е приключена" — по-настойчив, но неочакван: баджът остава и
  след като вече си видяла всичко.
  Нищо не се губи при изчистването — самата бележка си стои в списъка
  със значката за напомняне; тя е носителят на информацията, известието
  е само еднократният сигнал.
  Методът е проверен, че съществува в API-то на плъгина
  (`removeAllDeliveredNotifications(): Promise<void>`), но в кода има и
  проверка `if(!LN.removeAllDeliveredNotifications) return;` — по-стари
  версии на плъгина го нямат, а в браузър `nativeNotifications()` и без
  друго връща `null`.
  **Приключена/изтрита бележка вече спира да звъни ВЕДНАГА, не чак при
  следващото отваряне.** `remindableItems()` (значи и `checkRemindersNow()`
  за браузърния път) винаги е пропускала `status==='done'`/
  `tag===DELETED_TAG`, значи логиката си беше вярна — но `syncNativeReminders()`
  (насрочва/отменя нативните известия в самата операционна система) се
  викаше само при задаване/премахване на напомняне и при старт на
  приложението. Реален пропуск: маркираш бележка приключена или я триеш —
  ако вече Е НАСРОЧЕНО нативно известие (`LN.schedule()` отпреди), то си
  стои в ОС-а и ще звънне на часа си, докато не се отмени изрично; браузърният
  път е самоизлекуващ се (чете живото състояние на всеки тик), но нативният
  не е — насрочването е "еднократен изстрел", не проверява нищо повторно.

  бележка е допустима за напомняне: `markDoneBySwipe()`, `deleteBySwipe()`,

  3 реални находки, всичките поправени:**
  1. **`en` (английски) липсваха `onboardStepLook`/`onboardStepCleanup`**

     руски текст, само с излишен "мъртъв" дубликат преди него).
     Преместен на правилното си място в `en`, дубликатът в `ru` изчистен.
  2. **`langToggle` — мъртъв ключ**, дефиниран само в `bg`/`en` (липсваше
     в `ru`/`de`/`es`), но никъде не се четеше в кода (`LANG_NAMES`
     константата отдавна поема избора на език визуално). Изтрит и от
     двата места вместо добавен и в другите три — genuinely неизползван.
     Проверено с автоматична проверка (Playwright чете `Object.keys()`
     на всичките 5 `STRINGS[lang]` обекта и сравнява множествата) —
     сега и петте имат ТОЧНО еднакъв набор от 191 ключа.
  3. **`cycleData.cycleLength` — риск от безкраен цикъл в `phaseForDate()`
     при повредени данни.** `loadLocalCache()`/`loadFromCloud()`
     проверяваха само `typeof === 'number'`, не и диапазона — 0/
     отрицателна/`NaN`/`Infinity` стойност (напр. ръчно редактиран
     localStorage, или повреден Firestore документ) би направила
     обратната проекция `while(ls > d) ls.setDate(ls.getDate() -
     cycleLen)` безкрайна (при отрицателна крачка `ls` се отдалечава от
     `d`, вместо да се приближава). `computeCycleLength()` никога не
     връща такава стойност при нормална употреба — рискът е само при
     данни, стигнали дотук ОТВЪН нормалния път. И двата пътя за
     зареждане вече проверяват `isFinite(...) && > 0`, с fallback 28.
     Добавен е и евтин пазач (`guard++ < 5000`) директно в
     `phaseForDate()` самата — чисто defense-in-depth за бъдещ код,
     който би я извикал с данни извън `cycleData` глобала. Тествано с
     Playwright: зареждане със `cycleLength: -7` в localStorage се
     санира на 28; директен извик на `phaseForDate()` с невалидна
     стойност и дата ПРЕДИ първия период (форсира обратната проекция)
     завършва за милисекунди, не увисва.

  четивен текст на действия (не декоративна карта), нужна е по-добра
  четимост върху размазания фон. Без собствен `backdrop-filter` — менюто
  вече седи над `.ctx-backdrop` (самото то замъглено), размазването се
  вижда прозиращо без допълнителен разход.

  "затвори при клик извън" слушател (`document.addEventListener

  или друга бележка) продължава да затваря нормално — проверено изрично,

- **"Възстанови" от кошчето — `restoreFromTrash()`.** Дотогава единственият
  път назад от "Изтрити" беше Undo тостът веднага след трийсенето (виж
  `deleteBySwipe()`/`UNDO_MS`) — изтече ли той (или потребителят затвори/
  презареди приложението), бележката оставаше заклищена в кошчето, без
  никакъв бутон, до автоматичното изчистване след `TRASH_RETENTION_MS`
  (5 дни). Реален пропуск, симетричен на "Върни в предишното" (виж
  `reopenItem()` по-горе) — там имаше път назад, тук не.
  `softDelete()` вече пази постоянна следа НА САМИЯ обект (не само в
  затворената `restore()` функция, ползвана от Undo тоста):
  - бележка → `note.prevTag` (тагът преди трийсене).
  - подбележка → `trashed.restoreParentId` (id на бележката, от която е
    извадена — подбележка не може да носи собствен таг, значи при
    трийсене се "изважда" като самостоятелна бележка в кошчето, виж
    коментара в `softDelete()`).
  Бутонът "Възстанови" (`ICONS.replay`, най-отгоре в менюто — приоритетно
  действие, както "Върни в предишното") се показва САМО в кошчето
  (`inTrash===true`). `restoreFromTrash()`: ако има `restoreParentId` и
  родителят още съществува (не е и той изтрит) — връща я обратно В subs
  масива му; ако родителят вече не съществува — пада към общия случай
  (връща `tag` на `prevTag||null`, самостоятелна бележка), за да не се
  изгубят данните. Бележки, изтрити ПРЕДИ тази функция да съществува,
  нямат `prevTag`/`restoreParentId` — падат към същия fallback.
  **"Изтрий" в кошчето вече казва "Изтрий завинаги"** (`ctxDeleteForever`)
  — по-рано същият надпис като обикновеното (възстановимо) изтриване,
  въпреки че `softDelete()` за нещо вече в кошчето е окончателно (трие
  направо от масива). Ясно разграничение сега, когато вече има истински
  "Възстанови" до него, с което да се обърка.
  **Подбележка се връща ТОЧНО на старата си позиция сред подбележките на
  родителя** (`trashed.restoreIndex`), не в края — реален оплак след
  първата версия ("както е била", не просто "някъде в родителя").
  Ограничено до текущата дължина на `parent.subs` при възстановяване
  (`Math.min(restoreIndex, parent.subs.length)`) — родителят може
  междувременно да е получил/загубил други подбележки.
  **Покрай това: `trashed` обектът за подбележка вече копира ЦЯЛОТО ѝ
  състояние** (`color`/`reminderAt`/`reminderRepeat`/`completedAt`/
  `prevStatus`), не само `id`/`text`/`status`/`createdAt` — без това цвят и
  напомняне се губеха ТИХО при възстановяване от кошчето (макар Undo
  тостът да си беше наред — той пази ОРИГИНАЛНИЯ `sub` обект директно чрез
  затваряне, не опростен клонинг).
  `sanitizeImportedNote()` пази `prevTag`/`restoreParentId`/`restoreIndex`
  при внасяне на архив — без това възстановен от бекъп файл потребител би

- **Шрифтовете вече НЕ блокират зареждането — `<link>` вместо `@import`.**

  блок на приложението (стотици редове — цветове/layout/всичко). `@import`
  блокира парсирането на ЦЕЛИЯ stylesheet, в който живее, докато не се

  `<link rel="preconnect">` (по едно за `fonts.googleapis.com` и
  `fonts.gstatic.com`, второто с `crossorigin` — самите шрифтови файлове са
  на различен под домейн) + `<link rel="stylesheet">`, сложени рано в
  `<head>`, ПРЕДИ `<style>` блока. Browser preload скенерът ги открива
  веднага при получаване на суровия HTML (не чака парсера да стигне
  дълбоко в CSS-а), значи заявката тръгва паралелно с останалото, вместо
  да блокира. `display=swap` в самия URL остава непроменен — текстът се
  вижда веднага с fallback шрифт, замества се, щом истинският пристигне.
  Service worker-ът (`sw.js`) НЕ кешира тия заявки (не са same-origin, не
  са в `PRECACHE_URLS`) — офлайн изборът пада на системен шрифт, съзнателно
  приет компромис (виж `sw.js` документацията по-долу), непроменен от тая
  промяна.

  може да виси дълго/безкрайно. Резултат: потребителят изобщо не стига до

  кеш; `save()` праща целия `notes` масив при следваща промяна и без друго,
  значи облакът се изравнява сам.

  контролируем ръчно през `window.__resolveLateGet()`): екранът изчезва

  закъснял отговор от Firestore (пуснат ръчно след добавянето) НЕ трие
  новодобавената бележка.

- **Офлайн ЗАПИС — `enablePersistence()` + значка за синхронизация.**

  от сървъра и презаписваше локалния кеш, тоест бележката просто изчезваше
  пред очите на потребителя. Рискът стана реален точно когато `sw.js`
  позволи приложението да се отваря офлайн. `db.enablePersistence({
  synchronizeTabs:true})` (веднага след `firebase.firestore()`, ПРЕДИ всяка
  друга операция) слага опашката на диска. Провалът не е фатален и се

  обещанието от `set()` се изпълнява чак при потвърждение от СЪРВЪРА, значи
  "висящ запис" = "още не е в облака". Показва се едва след 2.5 сек, иначе

  синхронизирано" се увива на два реда на телефон и избутва търсенето и

  ред от inline `<script>`-а — ако `firebase` глобалната не съществува
  (скриптовете не са се заредили), целият inline скрипт хвърля грешка и
  дори кешираният `index.html` не помага.

  независимо от мрежата; Firestore записът е "fire and forget" отгоре.

  само fallback при офлайн (за да не засядат потребителите на стара версия,
  докато са онлайн — приложението се обновява при всеки push).

  минава първо през СОБСТВЕНИЯ HTTP кеш на браузъра (различен слой от

  си мисли, че тегли "най-новото". Резултат: потребител вижда стара
  функционалност дори онлайн, макар да презарежда — докладвано като
  "новата функция не работи", когато кодът всъщност си беше верен и

  всяко съмнение в самата логика). `{cache:'no-cache'}` форсира сървъра
  да потвърди свежест (ETag/Last-Modified), не да пропусне мрежата —
  същият подход вече ползван за precache-а в `install`. Версията на кеша
  е вдигната на v2, за да се изхвърли всеки вече кеширан стар `index.html`
  от преди тая поправка.

  isNativePlatform()`) — те вече тръгват от локални файлове, SW е излишен.
  Тествано с Playwright (routes фиктивен `firebase` обект + `context.
  setOffline(true)`): страницата се зарежда и рендира изцяло офлайн след
  първо онлайн посещение. **Кеширането на реалните gstatic Firebase SDK
  файлове не е тествано срещу истинска мрежа в тази среда** (пясъчникът

  файл поотделно точно заради такъв риск, но първото реално посещение
  "на живо" си струва да се провери.
- **Позициониране на приложението (важно за копирайта)** — "ден за ден":
  комфорт при решаване и приключване на много ежедневни задачи, организация
  и удобство. НЕ е хранилище за много бележки и информация. По тази причина
  обещанието "всичко се пази в облака" беше МАХНАТО от екрана за вход
  (`authSubtitle`/`authFeat1`) — некоректно е, откакто приключените се
  чистят сами. Ако някога се добавя нов маркетингов текст, да НЕ обещава
  дълготрайно съхранение.
- **Swipe жестове** — надясно = директно завършено, наляво = изтрито
  (soft delete) с 2.5 сек Undo тост + опит за haptic feedback
  (`navigator.vibrate` — не работи в Safari iOS, но безобидно другаде).
  При изтриване картата НЕ отлита настрани и не изчезва веднага (така беше
  преди) — връща се на място и остава видима като ПРОЗРАЧНА бележка
  (`.note.ghost-deleted`: прозрачен фон, пунктирана рамка, зачеркнат текст,
  `pointer-events:none`) точно докато тече Undo прозорецът. По заявка: да
  личи коя бележка си отива и да има към какво да се върнеш.
  Механиката: `deleteBySwipe()` хваща DOM елемента ПРЕДИ `softDelete()`
  (след него бележката е в кошчето и следващият `render()` няма да я
  нарисува), записва данните веднага, но ОТЛАГА `render()` с
  `ghostTimeoutId`. `UNDO_MS` (2500) е обща константа за тоста и за
  призрака — иначе едното свършва преди другото и или тостът предлага
  "Отмени" за изчезнала бележка, или картата виси без видима причина.
  Бутонът "Отмени" чисти `ghostTimeoutId` и рисува веднага.
- **Long-press меню** (~480ms задържане без движение) — Редактирай /

  дума под пръста и показва нативната лента Copy / Find Selection / Look Up
  ВЪРХУ нашето меню. Реално докладвано объркване — изглежда все едно
  "Копирай" ще копира само маркираната дума (копира цялата бележка, виж

  рано в разработката бяха временно скрити зад `isSatoriUser()`, после зад
  общата `hasAdvancedFeatures()` Premium проверка (виж Premium раздела
  по-долу) — и двете отменени изрично ("отключи функциите с цветовете...
  и напомнянето за всички потребители"). Гейтинг кодът е премахнат от
  трите места, където беше (бутоните в `renderCtxMenuMain()`,
  `noteColorAttr()`, значката в `itemRow()`) — вече само проверяват
  реалните данни (`item.color`/`item.reminderAt`), без потребителска
  проверка. `hasAdvancedFeatures()` функцията остава дефинирана (не се
  ползва никъде функционално в момента, само за бъдещо повторно
  използване, ако друга функция трябва да мине зад Premium).
- **Десктоп: мишка (`attachSwipeHandlers()`).** Дълго време жестовете
  слушаха САМО `touchstart`/`touchmove`/`touchend` — на компютър бележка
  НЕ можеше да се приключи, да се изтрие, нито менюто при задържане да се
  отвори. Реален докладван пропуск; сайтът е един и същ за телефон и
  компютър, но жестовете бяха писани само за пръст.
  Добавен е ОТДЕЛЕН път за мишка (`mousedown` + `contextmenu`), а туч
  пътят е оставен непокътнат. **Умишлено НЕ е преписано на Pointer
  Events**, макар че те биха обединили двата случая: туч пътят е минал
  през дълга поредица поправки за iOS (виж историята с клавиатурата
  по-горе) и не си струва да се разклаща заради десктопа.
  Три неща, които правят разликата между работещо и счупено тук:
  • **`mousemove`/`mouseup` са на `document`, ЕДИН БРОЙ за целия живот на
    страницата** (модулната `mouseDrag` пази коя бележка се влачи).
    `attachSwipeHandlers()` се вика при ВСЯКО рисуване — закачане на
    document слушател вътре в цикъла по бележките трупа по един на
    бележка на рисуване, тоест хиляди след няколко минути употреба.
    Първата версия го правеше точно така и беше поправена преди тест.
    На самата бележка не стават: влаченето спира в мига, в който
    показалецът излезе извън картата, а при плъзгане настрани това се
    случва постоянно.
  • **`justTouched()`** — тъч устройствата пускат СИНТЕТИЧНИ mouse
    събития след допир, значи без пазач всеки тап по телефона би минал и
    през пътя за мишка (двоен жест, двойно меню). Пази момента на
    последния допир, 700ms резерв.
  • **Десен бутон отваря същото меню.** На компютър това е далеч
    по-очакваният жест от задържане — задържането работи, но никой не се
    сеща да го пробва с мишка. Вътре в поле за писане нативното меню за
    текст се запазва.
  Бутоните вътре в бележката (таг, "+ добави", значка за напомняне) са
  изключени от влаченето — иначе клик върху тях започва жест.
  Тествано с Playwright, 10 проверки: плъзгане надясно/наляво с мишка,
  задържане, десен бутон, кратък клик (не прави нищо — да не се трие
  случайно при четене), 20 пре-рисувания не добавят НИТО ЕДИН нов
  document слушател; и от туч страна — плъзгането още работи, тапът НЕ
  отваря меню и не променя бележката.
- **Повтарящи се напомняния** (`item.reminderRepeat: null|'daily'|'weekly'`,
  чипове "Никога/Всеки ден/Всяка седмица" във формата за напомняне,
  `renderCtxMenuReminder()`) — избраното се пази в локална `selectedRepeat`

  повтори (daily = всеки ден от старта нататък; weekly = същия ден от
  седмицата) — ползва се от `calendarRemindersCountForKey()`, за да

  правило (същият `.note[data-colored]` селектор съвпада навсякъде).
- **Неонов режим** (`NEON_NOTES_KEY`/`applyNeonNotes()`, ключ `neonNotes` в

  прозрачните бележки) — по заявка: меките цветове са приятни, но за клиент
  може да е по-атрактивно нещо ярко. **Не променя запазените данни:**
  `item.color` си остава същият цвят от `PROFILE_COLORS`, сменя се само

  светват/угасват наведнъж, а връщането назад е без загуба.

  прилага се върху целия елемент, включително текста, и го прави нечетим.
  **Видът е "неонова тръба", не ярка запълнена карта:** тъмна основа
  (`#0E1015`) + слаб тон (`.16`) + плътна ярка рамка + външен ореол. Пробван
  беше и наситен пълнеж (`.42`), но там текстът губи четимост, а златното и
  теракотата излизат маслинено/тухлено. Ореолът е `box-shadow`, НЕ
  `filter:drop-shadow` — filter създава нов stacking context и би счупил
  изскачането на бележката над `.ctx-backdrop` при задържане.
  Тъмната основа е скопирана с `html.neon-notes:not(.glass-notes):not(

  тяхната собствена (иначе прозрачността се губи, а светлата тема
  потъмнява); там неонът идва само от рамката и ореола. Светлата тема е
  умишлено по-сдържана (по избор на потребителя): ореолът се губи върху
  кремавия фон, затова ефектът се носи от рамката.

  `background:var(--sw-active,var(--sw))`, а `html.neon-notes .ctx-menu

  акцентът на интерфейса остават меки; контрастът прави неона по-въздействащ.

- **Политика за поверителност / Общи условия** (`privacy.html`/`terms.html`)
  — самостоятелни статични страници, само bg+en (таб-превключвател горе),
  свързани от входния екран (`.auth-legal-links`) и от профил менюто.
  Чернова, писана добросъвестно, но **не е юридическа консултация** — при
  реално масово пускане е добре да мине преглед от юрист/счетоводител
  (особено GDPR детайлите — данни на администратора, приложимо право).
- **Обратна връзка** — линк в профила → "Помощ": иконка плик + самият
  адрес `info@iforget.eu` (Zoho Mail) като надпис, `mailto:` отдолу. Виж
  отделния раздел по-горе за пълния контекст и историята с вътрешната форма.
- **Меню на профила — акордеон с 4 разгъващи се групи, не плосък списък
  от ~13 реда и НЕ drill-down (подмяна на целия панел).** `renderProfileMenu()`
  показва имейл + цветове + 4 групови заглавия (Изглед/Данни/Акаунт/Помощ,
  генерирани през `profileGroupBlock(key, icon, label, innerHtml)`), всяко
  със стрелка `ICONS.chevronDown` вдясно (`.action-chev`), СОЧЕЩА НАДОЛУ по
  подразбиране. Клик на заглавие разгъва съдържанието му (`.group-content`)
  НА МЯСТОТО, под самото заглавие — останалите групи се избутват надолу,
  `.action-chev` се завърта на 180° (`.action-chev.open`). Само ЕДНА група
  е отворена наведнъж (акордеон) — клик на друго заглавие затваря текущо
  отворената и отваря новата; клик на СЪЩОТО заглавие просто я затваря.
  Разпределение: **Изглед** = прозрачни бележки + лява ръка; **Данни** =
  Твоят преглед/Календар/Експорт/Импорт/Статистика (админ); **Акаунт** =
  смяна на парола/имейл + Изход/Изтриване на профила (danger бутоните,
  преди отделни в дъното на плоското меню, сега вътре в тази група);
  **Помощ** = Обратна връзка + Поверителност/Общи условия. Линковете
  "Поверителност"/"Общи условия" в Помощ са по ситен шрифт (`.small-link`,
  `font-size:10px`, `font-weight:400`) по изрична молба — по-малко визуално
  тегло от истинските действия. Текстът им е златист (`.small-link
  .action-label{color:var(--gold);}`), но ИКОНИТЕ им НЕ — остават сиви/
  приглушени (наследяват `var(--text-dim)` от `.small-link`, защото иконата
  е "брат" елемент на `.action-label`, не негово дете) — по изрична молба
  само текстът да е златист, не и иконата.
  **Шрифт/еднолинейни етикети** (по изрична молба): базовият `font-weight`
  на `.profile-panel button.action, .profile-panel a.action` е 500 (не
  600 — по-тънък). Панелът е `width:254px` (от 230px) и отстъпът на
  редовете вътре в група е `padding-left:22px` (от 30px) — освободено
  място, за да се събира максимално изречение на ЕДИН ред. Самият текст на
  всеки бутон е обвит в `<span class="action-label">` (помощна функция
  `L(text)` в `index.html`, ползвана и от `profileGroupBlock()`) — ТОЧНО
  този `<span>`, не целият flex контейнер на бутона, носи
  `white-space:nowrap;overflow:hidden;text-overflow:ellipsis` — иначе
  иконата/чекмарк-а/стрелката вдясно биха се свили заедно с текста. Ако
  някой бъдещ етикет е твърде дълъг дори при тази ширина — отрязва се с
  "…" вместо да чупи на 2 реда (елегантно деградиране, не бъг).
  **Отварянето/затварянето на групата при клик е ПРЯКА DOM манипулация
  (class toggle + `content.style.maxHeight = content.scrollHeight + 'px'`),
  НЕ re-render** — точно за да остане плавната CSS `transition:max-height`
  анимация (не може да се анимира към `auto`, затова JS-ът смята и задава
  конкретен `px`). `let profileOpenGroup` (module-level, до `profileColor`)
  пази КОЯ група е последно отворена, за да оцелее през истинските
  `renderProfileMenu()` re-render-и (смяна на цвят, toggle на прозрачни
  бележки/лява ръка, връщане от под-форма като "Смени парола") — в тия
  случаи групата се разгъва обратно МОМЕНТАЛНО, без анимация (само user
  клик анимира). Нулира се на `null` само в `closeProfilePanel()` (целият
  панел се затваря), за да тръгва свежо следващия път. Всички под-форми/
  изгледи, достъпни ОТ дадена група (`renderPasswordForm()`/
  `renderEmailForm()`/`renderDeleteAccountForm()` от Акаунт,
  `renderMyReview()`/`renderCalendarView()`/`renderAdminStats()` от Данни),
  при "Отказ"/"Назад" викат просто `renderProfileMenu()` — групата се
  разгъва автоматично обратно благодарение на `profileOpenGroup`, не се
  налага отделна логика за "коя група да отворя". Вече покритият
  `#profilePanel` `mousedown`/`stopPropagation()` фикс (виж по-долу) важи
  автоматично и за груповите заглавия — не е нужен нов код за това.

## Постоянни правила (винаги, без изключение)

- **Само SVG икони, никога emoji** за бутони/иконки в интерфейса (виж
  `ICONS` обекта в `index.html`) — emoji изглежда различно на различни
  устройства/ОС версии, SVG е консистентно навсякъде. Декоративни стрелки
  в обикновен текст (напр. "активна → в прогрес") не са "икона" в този
  смисъл и са ОК. При добавяне на нова визуална иконка — винаги нов запис
  в `ICONS`, никога суров emoji символ в HTML/JS низовете.
- **Фоновата ginkgo снимка (`bg-dark-v3.jpg`/`bg-light.jpg`) трябва да е на
  `html`, НЕ на `body`.** background на елемент спира точно на неговата
  собствена изчислена височина, освен ако е на html (кореновият елемент по
  спецификация винаги покрива цялото платно на страницата, без значение от
  вътрешния layout). `body` затова е БЕЗ собствен `background-color` —
  иначе плътният му цвят би скрил образа на html. (Историческа бележка:
  преди layout промяната по-долу body преливаше физически извън собствената
  си кутия при дълъг списък бележки, което беше ДОПЪЛНИТЕЛНА причина фонът
  да е на html — вече не прелива (`body{height:100vh;overflow:hidden}`,
  скролът е вътре в `#activeArea`), но фонът си остава на html, по-безопасно
  е и няма нужда да се пипа/тества отново.)
- **Layout: topbar/bottombar са фиксирани "региони", `#activeArea` (`<main>`)
  е ЕДИНСТВЕНИЯТ вътрешно скролиращ елемент** (`body{height:100vh;
  overflow:hidden}`, `main{flex:1 1 auto;min-height:0;overflow-y:auto}`) —
  вместо предишния модел с `position:sticky` topbar + скрол на цялата
  страница (капризен на мобилни браузъри — адресна лента, клавиатура).
  Затова `window.scrollY`/`window.scrollTo`/`document.documentElement.
  scrollHeight` вече НЕ се ползват никъде за списъка с бележки — вместо тях
  `activeArea.scrollTop`/`.scrollTo()`/`.scrollHeight` (виж
  `scrollToBottom()`/`updateJumpVisibility()`/pull-to-refresh IIFE-то/
  `openTagPicker()`/`closeTagPicker()`). `min-height:0` на `main` е
  задължително — flex елемент има `min-height:auto` по подразбиране (расте
  до съдържанието си вместо да се свива до наличното място), което би
  счупило `overflow-y:auto`.
  **Реален браузърен бъг, хванат и заобиколен при тази промяна:**
  `overflow:auto` + `justify-content:flex-end` на ЕДИН И СЪЩ flex контейнер
  дава грешно `scrollHeight`, когато съдържанието прелее ОТГОРЕ (leading
  overflow) — `scrollHeight` остава равен на `clientHeight`, все едно няма
  какво да се скролва, макар списъкът реално да прелива (needed за "къс
  списък застава долу, залепен до полето за писане" ефекта). Затова
  скролът (`main{overflow-y:auto}`) и подредбата (`justify-content:flex-end`
  за bottom-anchor) са на ДВА различни елемента: `main#activeArea` (обикновен
  блоков контейнер, скролва) → дете `.notes-inner#notesInner` (`display:flex;
  justify-content:flex-end;min-height:100%`, подрежда). `render()` пише
  `innerHTML` в `notesInner`, НЕ директно в `activeArea`.
- **Позициониране на плаващи панели (tag-picker/ctx-menu/lang-picker) спрямо
  екранната клавиатура: НИКОГА само `window.innerHeight`.** На телефон
  клавиатурата НЕ смалява `window.innerHeight` — само `window.visualViewport
  .height`/`.offsetTop` реално отразяват видимата зона над клавиатурата.
  Панел, позициониран само спрямо `innerHeight`, може да увисне (частично
  или изцяло) зад клавиатурата, недостижим — виж `visibleViewportBox()` в
  `index.html` (ползвана от `positionTagPicker()`) и слушателя за
  `visualViewport`-а `resize` събитие, нужен ЗАЕДНО с проверката — самата
  проверка веднъж при отваряне не стига, трябва да следи и последващото
  отваряне на клавиатурата (напр. тапване на полето за нов таг СЛЕД като
  picker-ът вече е отворен).
  **Същия принцип важи и за `scrollIntoView()`, не само за ръчно
  позициониране** — `focusAndReveal(inp)` (използва се за sub-input И
  `.edit-input` при редакция на бележка) първоначално викаше
  `scrollIntoView()` ЕДНОКРАТНО, веднага след `.focus()`. Реален докладван
  бъг: клавиатурата на телефона се отваря АНИМИРАНО (~250-300ms) — в
  момента на `.focus()` видимата зона все още е "пълна", `scrollIntoView()`
  скролва спрямо ТОВА, а после клавиатурата продължава да "изяжда" видимата
  зона и полето пропада зад нея, макар кодът вече веднъж да го е "показал".
  Фиксът: `focusAndReveal()` сега преизчислява (`inp.scrollIntoView(...)`)
  на ВСЯКО `visualViewport` `resize`/`scroll` събитие, докато полето остане
  фокусирано (спира на `blur`, виж `stopViewportReveal()`) — същия похват
  като `repositionTagPickerOnScroll()`, приложен и тук.
  **Второ кръгче поправки (след като полето вече ставаше видимо, но над
  него оставаше голяма празна ивица фон, скриваща предходни бележки):**
  две отделни причини, поправени заедно. (1) `focusAndReveal()` викаше
  `scrollIntoView({block:'center'})` — центрира полето в наличното
  пространство вместо да го долепи до долния край, което буквално хаби
  място под него (там, където реално има повече бележки за показване
  отгоре). Сменено на `block:'end'` — `main{padding-bottom}` вече пази
  точно нужния резерв над клавиатурата, така че полето застава плътно
  без да опира буквално в клавиатурата (самото поле си има вътрешен
  padding/бордюр). (2) `activeArea.scrollTop` НЕ се преизчислява
  автоматично само защото `main`-ът (== `activeArea`) се е свил заради
  клавиатурата (виж `body{height:var(--app-height)}`) — старата стойност
  остава технически "валидна", просто вече не сочи най-долу спрямо
  по-малкия видим прозорец. За случая с полето за НОВА бележка (за
  разлика от редакция, където `focusAndReveal()` се грижи индивидуално)
  добавена изрична котва в `handleViewportResize()`:
  `if(document.activeElement === noteInput){ activeArea.scrollTo({top:
  activeArea.scrollHeight, behavior:'auto'}); }`.
  **Трето кръгче — реалният сигнал, че цялата ръчна JS схема не стига:**
  след горните два фикса, `#noteInput` (полето за НОВА бележка, живее
  ВЪТРЕ в `.bottombar{position:fixed}`, за разлика от `.edit-input`, което
  е в нормалния scroll flow) продължи да показва празнина на реално
  устройство — потвърдено с `?debugviewport=1` overlay screenshot от
  друг сценарий (подбележка, работещ коректно), докато точно за
  счупения сценарий overlay-ят липсваше от снимката (вероятно паникирал/
  избутан извън видимата зона — самият overlay е `position:fixed;top:...`,
  същия клас елемент като bottombar-а). Класически признак за реален iOS
  Safari бъг: фокус върху `<input>` ВЪТРЕ в `position:fixed` контейнер
  кара браузъра сам да "панира"/премести VISUAL VIEWPORT-а (независимо от
  `visualViewport.offsetTop`, което следим), докато LAYOUT VIEWPORT-ът
  (спрямо който `position:fixed` се позиционира) остава непроменен —
  никаква комбинация от ръчни `scrollTo`/`transform` изчисления не може
  надеждно да компенсира това, защото ние виждаме само СЛЕДСТВИЯТА
  (`visualViewport` стойности), не самата причина.
  **Фиксът в основата, вместо поредна ръчна кръпка:** добавен
  `interactive-widget=resizes-content` към `<meta name="viewport">` (iOS
  17+ Safari, съвременен Chrome/Android) — казва на браузъра сам да
  смалява LAYOUT viewport-а (не само visual viewport) при клавиатура,
  така че `window.innerHeight`/`100vh`/обикновен CSS layout автоматично
  отразяват видимата зона, без ръчни `visualViewport` изчисления изобщо.
  На браузър без поддръжка стойността просто се игнорира — старият JS
  fallback (`updateAppHeight()`/`handleViewportResize()`) продължава да
  работи както досега, така че промяната е обратно съвместима. Очакван
  ефект при поддръжка: `offset` в `handleViewportResize()` пресмята ~0
  (`window.innerHeight` вече съвпада с `visualViewport.height`), transform-ът
  на bottombar-а остава празен низ — не е бъг, просто вече не е нужен.
  **Потвърдено на реално устройство: този фикс НЕ помогна** (може би
  версията на iOS не поддържа `interactive-widget=resizes-content`, или
  проблемът изобщо не е layout-viewport resize, а нещо по-фундаментално).
  Ново доказателство от следващ real-device скрийншот: самата `#viewportDebug`
  кутийка (`position:fixed`, закачена за LAYOUT viewport-а) се "изтласква"
  почти изцяло извън видимия екран при фокус на input — виждаше се само
  последният ѝ ред. Това потвърждава директно (не по индиректни следствия),
  че ВИЗУАЛНИЯТ viewport реално се измества/панира спрямо LAYOUT viewport-а
  при тази клавиатурна анимация, независимо от `interactive-widget`
  директивата. Добавена компенсация в `updateViewportDebug()`: кутийката
  вече сама следи `visualViewport.offsetTop` и мести собствения си `top`,
  за да остане видима дори ПО ВРЕМЕ на самото паниране — целта е следващият
  screenshot да съдържа реалните числа (`visualViewport.height`/`offsetTop`)
  В МОМЕНТА на бъга, вместо да гадаем от косвени признаци. Диагностика,
  не поправка — истинският root-cause фикс чака тези числа.
  **НАМЕРЕН ROOT CAUSE (реални числа от следващия screenshot):**
  `window.scrollY` реално се покачваше при бъга (0 → 107 → 211px, синхронно
  с `visualViewport.offsetTop`) — не просто визуално "паниране" на
  visual viewport-а, а истинско СКРОЛВАНЕ на самия document. Причина:
  `overflow:hidden` беше сложен само на `body`, НЕ и на `html`. В standards
  mode `document.scrollingElement` е `<html>`, не `<body>` — заключване
  само на body не пречи на iOS Safari да скролне `<html>` директно чрез
  нативната си "покажи фокусирания input" логика, когато input-ът е вътре
  в `position:fixed` контейнер (`#noteInput` в `.bottombar`). Резултатът:
  целият фиксиран layout (topbar/bottombar/фон) се "занишкваше" в синхрон
  с document-а, оставяйки видима "празнина" — реално ИЗМЕСТЕН фон
  (повтарящ се ginkgo tile, затова изместването изглежда като празно
  пространство), не липсващо съдържание.
  **Фиксът:** `overflow:hidden` добавен и на `html` (не само `body`) —
  двата елемента заедно се заключват срещу document-scroll, класически
  правилен похват за "заключена" мобилна страница на iOS Safari.
  **И ТОВА не помогна — но следващите числа дадоха пълната картина.**
  При бъга (нова бележка, отворена клавиатура) реалните стойности бяха:
  `innerHeight: 433`, `visualViewport.height: 433`, `--app-height: 433px`,
  `visualViewport.offsetTop: 211`, `window.scrollY: 211`.
  Разчитането им: документът е ТОЧНО колкото видимата зона (нищо не може
  да се скролва — html/body са `overflow:hidden` с точната височина), а
  Safari въпреки това е изместил ВИЗУАЛНИЯ прозорец 211px надолу, отвъд
  края на документа. Значи:
  - "празнината" НЕ е празно място в приложението — това е зоната ПОД
    края на страницата, където се вижда само фоновият тайл на `html`
    (затова изглежда като безкраен фон с гинко листа, а не като липсващо
    съдържание);
  - полето за писане е долепено долу, защото `position:fixed` елементите
    на iOS се закачат за ВИЗУАЛНИЯ прозорец, не за layout-а — оттам и
    впечатлението, че "фонът се показва до средата на екрана";
  - `overflow:hidden` не може да го спре, защото това НЕ е document
    scroll, а pan на визуалния прозорец (браузърен слой над layout-а),
    макар `window.scrollY` да го отразява.
  Изместването е чист остатък от нативната логика "покажи фокусирания
  input": Safari го смята ПРЕДИ layout-ът да се свие и не го връща,
  след като свиването вече е освободило нужното място (двойна
  компенсация). **Текущият опит за фикс:** нулиране в
  `handleViewportResize()` — `if(window.scrollY !== 0) window.scrollTo(0,0);`
  (при заключен документ всяко ненулево `scrollY` е точно този паразитен
  pan; проверката пази от безкраен цикъл). Стандартен iOS workaround, но
  НЕ е гарантирано, че Safari приема нулирането — чака потвърждение от
  реално устройство. (Остана в кода като предпазна мрежа; сам по себе си
  НЕ реши бъга.)
  **РЕШЕНИЕТО (потвърдено от потребителя кое работи и кое не):** решаващата
  улика дойде от самия потребител — полето за ПОДбележка работеше
  безупречно през цялото време, докато полето за нова бележка беше счупено
  при абсолютно същата клавиатура. Единствената разлика между тях е
  СТРУКТУРНА: полето за подбележка е в нормалния поток (вътре в
  скролиращия `main#activeArea`), а `#noteInput` беше вътре в
  `.bottombar{position:fixed}`. Точно фиксираният контейнер е това, което
  кара iOS Safari да панира визуалния прозорец при фокус.
  Затова `.bottombar` вече е **обикновено flex дете на `body`**
  (`flex-shrink:0`, плътен `background:var(--bg)`), точно като `.topbar` —
  трите елемента (topbar / main `flex:1` / bottombar) се смятат от един и
  същ layout pass върху `body{height:var(--app-height)}`, тоест лентата
  стои над клавиатурата по чиста геометрия. Ръчният
  `bottomBar.style.transform = translateY(-offset)` в
  `handleViewportResize()` е ПРЕМАХНАТ — с лента в потока той би се
  наслагвал върху вече правилната позиция и би вдигал лентата двойно.
  `main{padding-bottom}` намален от `134px` (резерв за плаващата лента) на
  `16px` (само дишане под последната бележка).
  **Защо сега сработи, а предишният същ опит беше обърнат:** тогава
  липсваха три неща, добавени междувременно —
  `interactive-widget=resizes-content` (layout viewport реално се свива;
  потвърдено с числа: `innerHeight == visualViewport.height == 433`),
  `overflow:hidden` и на `html`, и `.bottombar.editing-hide` (което маха
  точно регресията — застъпване с полето за редакция — довела до
  предишното обръщане).
  Проверено с Playwright върху реалната страница: разстоянието последна
  бележка → лента е **22px и без, и с клавиатура** (при `--app-height`
  844 → 433), тоест празнината не расте изобщо; при `.editing-hide`
  списъкът поема освободеното място коректно.
  **✅ ПОТВЪРДЕНО ОТ ПОТРЕБИТЕЛЯ на реален iPhone — и трите сценария (нова
  бележка, подбележка, редакция) работят.** Временният диагностичен overlay
  (`#viewportDebug` + `?debugviewport=1` + `updateViewportDebug()`), с
  който бяха хванати числата по-горе, е ПРЕМАХНАТ след потвърждението —
  ако някога пак потрябва, шаблонът е: `position:fixed` кутийка, която сама
  компенсира `visualViewport.offsetTop` за собствения си `top` (иначе при
  точно този бъг се изтласква извън екрана и скрива тъкмо числата, които
  трябва да покаже).
  **Поуката за занапред:** решаващата стъпка не беше поредната кръпка, а
  сравняването на СЧУПЕН с РАБОТЕЩ случай в същата среда (нова бележка
  срещу подбележка) — разликата между тях сочи причината далеч по-надеждно
  от разсъждения върху счупения случай сам за себе си. Преди това четири
  последователни "поправки" (`-webkit-overflow-scrolling` премахване,
  непрекъснат `scrollIntoView`, `block:'end'` + scrollTop котва,
  `interactive-widget`, `overflow:hidden` на html) не решиха проблема,
  защото всяка атакуваше следствие, а не причината.
- **Бутони ВЪТРЕ в #ctxMenu/#profilePanel, които подменят innerHTML НА
  МЯСТО (панелът остава отворен, само превключва изгледа — напр. "Цвят"/
  "Напомняне"/"назад" в ctx-менюто, "Твоят преглед"/"Календар" в профила),
  ЗАДЪЛЖИТЕЛНО се нуждаят `#ctxMenu`/`#profilePanel` да имат собствен
  `mousedown` слушател с `e.stopPropagation()` (виж го точно преди
  глобалния "затвори при клик отвън" `document` слушател).** Причина:
  подмяната на `innerHTML` прави оригиналния `e.target` DETACHED от
  документа В СЪЩИЯ момент, докато СЪЩОТО mousedown събитие все още
  "изкачва" (bubble) към `document` — глобалният outside-click слушател там
  проверява `panel.contains(e.target)`, а за detached възел това връща
  `false` (все едно кликът е бил ИЗВЪН панела) → погрешно затваря панела
  веднага след като той тъкмо е превключил изгледа. Реален бъг, хванат
  точно с "Цвят" бутона — тапваш го и веднага се връща на бележката, вместо
  да покаже кръгчетата за избор.
- **JS позициониране на панел, "закачен" за конкретен бутон
  (`panel.style.right = ...`), трябва да провери `leftHanded`, не само CSS
  `html.left-handed .topbar-row{flex-direction:row-reverse;}`.** CSS-ът
  визуално мести бутона (напр. `#userChip`) в лявата страна на екрана, но
  JS изчисление, което винаги закача панела с `right:` спрямо десния край
  на бутона, не "знае" за това — панелът остава закотвен все едно бутонът
  пак е вдясно и излиза извън/накрая на екрана, скрит. Виж
  `openProfilePanel()` — при `leftHanded` трябва изрично `panel.style.left
  = rect.left + 'px'; panel.style.right = 'auto';` вместо обратното.
  Аналогично на `edgeAlignedLeft()` (tag-picker/ctx-menu), само че тук
  панелът винаги е закачен директно за бутона, не за края на карта.

## Известни ограничения

- `navigator.vibrate()` не работи в Safari iOS (Apple, native-only) —
  извиква се навсякъде безобидно, реално вибрира само на Android/Chrome.
- Home Screen quick-add shortcut изисква по-нова iOS Safari версия за
  пълна поддръжка на manifest `shortcuts`.
- `share_target` (Web Share Target) изобщо не се поддържа от iOS Safari за
  уеб приложения — само Android/Chrome. На iPhone/iPad ще проработи само
  ако iForget стане native приложение в App Store.
- `:has()` CSS селектор (използван за разстоянието след група с
  подбележки) изисква Safari 15.4+/iOS 15.4+.
- Няма build/test pipeline.

## Работен процес при промени

1. `git pull -q origin main` в локалния клонинг преди всяка промяна.
2. Редакция на `index.html` (и/или `manifest.json` и др.).
3. Проверка на JS синтаксиса преди push — извличане на съдържанието между
   `<script>...</script>` и `node --check` върху него (регекс екстракция,
   не има отделен `.js` файл в repo-то).
4. `git add -A && git commit -m "..." && git push -u origin main`.
5. Изчакване ~20 сек и проверка на GitHub Actions run-а за
   `conclusion:"success"`, преди да се докладва успех на потребителя.
6. Отговор винаги на български, с препратка към живия адрес
   `https://iforget.eu` и напомняне за hard refresh (кешът на браузъра/PWA
   понякога пази старата версия).

Всяка промяна на UI/UX се комуникира и потвърждава на български — user-ът
пише с чести правописни грешки/фонетична транслитерация, но намеренията
обикновено стават ясни от контекста; при истинска неяснота — питай.

## Брандиран линк за забравена парола — ДЕПЛОЙНАТО И РАБОТЕЩО (потвърдено)

Домейн верифициран в Resend (SuperHosting.bg DNS: DKIM/SPF/MX/DMARC
записи), `RESEND_API_KEY` secret зададен, `firebase deploy --only
functions,firestore:rules` мина успешно, реален тест през "Забравена
парола?" на iforget.eu потвърди — писмото идва от `noreply@iforget.eu`.
(Ако тестваш пак и видиш стар подател — кеширана страница в браузъра,
hard refresh `Cmd+Shift+R` решава, не е бъг в кода — вече се е случвало.)

Firebase-генерираните reset линкове винаги сочат към `*.firebaseapp.com`
(iforget.eu е на GitHub Pages, не Firebase Hosting, затова Console
"Action URL" настройката не помага). Решението — Cloud Function, точно
както е в `neshovska/glowtrack` (`functions/index.js:sendBrandedPasswordReset`,
виж го там за пълния rationale/коментари) — е написано и в тоя repo, но
разликата с glowtrack: **изпраща през Resend (HTTP API), не през SMTP/
nodemailer**, защото имейлът е Resend (`noreply@iforget.eu`, само за
изпращане, "Enable Receiving" изключено нарочно), не пълна Zoho кутия.

**Файлове в repo-то** (нови): `functions/index.js` (самата функция),
`functions/package.json`, `functions/.eslintrc.js`, `firebase.json`,
`.firebaserc` (project ID `iforgetbg`), `firestore.rules` (добавен нов
блок за `password_reset_throttle` — `allow read, write: if false;`,
достъпна само от Admin SDK, никога от клиента).

**Логика на `sendBrandedPasswordReset`** (`onCall`, region `europe-west1`
— трябва да съвпада с клиентския `firebase.app().functions('europe-west1')`
в `index.html`, иначе compat SDK търси в `us-central1` и хвърля not-found):
1. Anti-abuse throttle (Firestore транзакция, `password_reset_throttle`
   колекция) — 3/час per имейл + 20/минута общо, проверено ПРЕДИ
   `generatePasswordResetLink`, за да важи и за несъществуващи имейли.
2. `admin.auth().generatePasswordResetLink(email, {url:'https://iforget.eu/'})`
   → извлича `oobCode`-а от резултата → строи
   `https://iforget.eu/reset-password.html?mode=resetPassword&oobCode=...`
   (`reset-password.html` вече съществуваше в repo-то отпреди, приема
   точно тия параметри — не е пипана).
3. Изпраща през `fetch('https://api.resend.com/emails', ...)` с `Authorization:
   Bearer <RESEND_API_KEY secret>`, `from: 'iForget <noreply@iforget.eu>'`.
4. **Винаги връща `{ok:true}`**, дори за несъществуващ имейл/throttled
   заявка (anti-enumeration — клиентът не може да различи "имейлът не
   съществува" от "успешно изпратено"). `index.html:handleForgotPassword()`
   вече е обновена да вика тази функция (`functionsInstance.httpsCallable(
   'sendBrandedPasswordReset')`) вместо стария `auth.sendPasswordResetEmail()`.

Всички стъпки по-долу вече са изпълнени от потребителя (запазено само за
референция, ако функцията трябва да се пре-деплойва след бъдещи промени
в `functions/index.js`):
1. `firebase login` + `firebase use iforgetbg` (локално, на компютъра ѝ).
2. `firebase functions:secrets:set RESEND_API_KEY` (НИКОГА не се пише в
   repo-то/код — secret е в Google Cloud Secret Manager).
3. `firebase deploy --only functions,firestore:rules`.
4. Реален тест — потвърдено работещо.

## Брандиран email verification (потвърждение на регистрация) — ДЕПЛОЙНАТО

Потребителят забеляза, че само reset-паролата беше брандирана — имейлът
"Провери пощата си и потвърди имейла си" при регистрация още идваше от
Firebase-default `noreply@iforgetbg.firebaseapp.com`, защото никога не е
бил пипан (само `sendBrandedPasswordReset` съществуваше). Решението е
**точно същия принцип, копиран 1:1**:

- `functions/index.js:sendBrandedEmailVerification` (`onCall`) — вместо
  `generatePasswordResetLink` използва `admin.auth()
  .generateEmailVerificationLink(email, {url:'https://iforget.eu/'})`,
  извлича `oobCode`-а, строи `https://iforget.eu/verify-email.html?
  mode=verifyEmail&oobCode=...`, изпраща през същия Resend `fetch()` (пак
  `RESEND_API_KEY` secret — вече зададен, не трябва нов). Throttle е
  **по-прост** от password reset — изисква `request.auth` (потребителят
  вече е логнат/регистриран точно преди това), значи няма anti-enumeration
  нужда (за разлика от password reset, достъпен за всеки нелогнат с
  произволен имейл) — само `email_verification_throttle` колекция, 5/час
  per uid, без глобален лимит.
- `verify-email.html` (ново, копие на `reset-password.html` по структура)
  — чете `?mode=verifyEmail&oobCode=...`, вика `auth.applyActionCode(oobCode)`
  (по-просто от password reset — само потвърждава кода, няма форма за нова
  парола/данни от потребителя). **Умишлено НЕ е добавена в
  `scripts/sync-www.js` FILES_TO_COPY** (същата логика като
  `reset-password.html` — само за уеб flow, отваря се от имейл линк в
  браузър, не й трябва вътре в нативния апп).
- `firestore.rules` — нов блок `email_verification_throttle` (`allow read,
  write: if false;`, само Admin SDK).
- `index.html` — нова споделена `sendVerificationEmail()` функция (вика
  `functionsInstance.httpsCallable('sendBrandedEmailVerification')({})`,
  **без email параметър** — Cloud Function-ът чете `request.auth.token.email`
  директно, не приема произволен email от клиента, за разлика от password
  reset, който МОРА да приема email от нелогнат клиент). Ползва се от
  ДВЕ места: `resendVerifyEmail()` (банерът "изпрати пак") и signup
  handler-а (`action.then(cred => cred.user && sendVerificationEmail()...)`).
  И двете преди викаха `user.sendEmailVerification()` директно. Същия
  FALLBACK принцип като `handleForgotPassword()` — при
  `'functions/not-found'` (функцията още не е деплойната) пада обратно
  към стария `currentUser.sendEmailVerification()`, за да не остане
  верификацията чупена в прозореца преди deploy.

~~**Остава**~~ — **ДЕПЛОЙНАТО** (потвърдено от потребителя, `firebase
deploy --only functions,firestore:rules` от собствения ѝ Mac,
`functions[sendBrandedEmailVerification(europe-west1)] Successful update
operation.`). Реален тест (регистрирай тестов акаунт или "изпрати пак" от
банера, провери дали писмото идва от `noreply@iforget.eu`) остава за
следващия път, когато има повод — не е блокиращо.

## Premium/Stripe инфраструктура — ПОДГОТВЕНА, но НЕВИДИМА за реални потребители

По изрична молба: "искам да имам всички опции подготвени, после кто
реша да пускам плащане само активирам и готово, но за момента ще
мъчим безплатно да видим колко ще се вържат." Целта: целият платежен
път е написан и работи, но е напълно скрит/неактивен, докато
потребителят изрично не "щракне ключа" — БЕЗ redeploy на код, само
промяна на един Firestore документ.

**Главният ключ** — `config/premium` документ във Firestore, поле
`enabled: boolean`. Публично четим (`allow read: if true`), пишем
САМО ръчно от Firebase Console (rules забраняват клиентски write).
Ако документът изобщо не съществува (сегашното състояние — никой не
го е създавал още), `loadPremiumConfig()` в `index.html` третира това
като `enabled: false` — т.е. **не е нужно нищо да се създава предварително,
Premium е скрит по подразбиране без никакво действие**. За да "активира"
Premium занапред, потребителят просто създава/редактира тоя документ
в Firebase Console → Firestore → `config/premium` → `enabled: true`.

**Ценообразуване** (потвърдено с потребителя): Месечен €2.99/месец +
Годишен €19.99/година (-44% спрямо 12×месечен), и двата с вграден
14-дневен безплатен trial (конфигуриран в `subscription_data.trial_period_days`
на самата Checkout Session, не в Stripe Product-а — картата се пази при
подписване, но не се таксува до края на 14-те дни).

**Клиентска логика (`index.html`)**:
- `let premiumLaunched` — зареден веднъж при старта на апа (`loadPremiumConfig()`,
  извикана от init секцията долу до `requestPersistentStorage()`), НЕЗАВИСИМО
  от логин статус.
- `let userIsPremium` — зареден от `entitlements/{uid}` при всеки успешен
  логин (`loadEntitlement()`, извикана от `auth.onAuthStateChanged()` ПРЕДИ
  `loadFromCloud()`), нулиран на `false` при логаут/смяна на акаунт.
- `function hasAdvancedFeatures(){ return isSatoriUser() || userIsPremium; }`
  — заменя старите директни `isSatoriUser()` проверки за Цвят/Напомняне (3
  места: бутоните в `renderCtxMenuMain()`, `noteColorAttr()`, значката за
  напомняне в `itemRow()`). **Админ профилът винаги минава, независимо от
  реален Stripe статус** — общото правило от по-рано в документа. Чисто
  административни неща (Статистика, Satori таг) си остават `isSatoriUser()`
  директно — НЕ минават през `hasAdvancedFeatures()`, не са Premium функции.
- **Акцентният цвят на профила — отключен за всички потребители** (текущо
  състояние). Кратка история: за кратко беше частично заключен зад Premium
  (`PROFILE_COLORS_FREE = ['', '#6E8FBF', '#C6A052']` — само по подразбиране
  + синьо + жълто свободни, останалите 4 заключени с катинарче/grayscale),
  после отменено изрично в същия разговор ("отключи функциите с цветовете
  в профила... за всички потребители"). `PROFILE_COLORS_FREE` константата и
  `.color-sw.locked` CSS правилото са премахнати — всичките 7 цвята в
  `PROFILE_COLORS` отново са directly избираеми за всеки, без проверка.
- `renderProfileMenu()` показва (само ако `premiumLaunched && !isSatoriUser()`):
  ако `userIsPremium` → злат бадж "Premium активен"; иначе → злат бутон
  "Ъпгрейд до Premium" (`data-action="premium-upgrade"`) → `renderPremiumPlans()`.
- `renderPremiumPlans()` (нов, до `renderDeleteAccountForm()`) — 2 бутона
  (месечен/годишен), вика `createCheckoutSession` Cloud Function, редиректва
  към `session.url` (Stripe-хостнатата Checkout страница — картата НИКОГА
  не минава през нашия код).
- CSS gotcha (документиран директно в CSS коментар): `.profile-panel .premium-cta`
  (2 класа) губи от по-специфичното `.profile-panel button.action` (тип+2 класа)
  — трябва `.profile-panel button.action.premium-cta` (3), същия капан като
  `.action.danger` по-горе. Ценовите бутони (`.premium-plans .action-label`)
  изрично РАЗРЕШАВАТ чупене на 2 реда (override на глобалния nowrap+ellipsis)
  — по-добре 2 реда, отколкото да изчезне "-44%" зад "...".

**Сървърна логика (`functions/index.js`)**:
- `stripeSecretKey`/`stripeWebhookSecret` — Firebase secrets (`firebase
  functions:secrets:set STRIPE_SECRET_KEY`/`STRIPE_WEBHOOK_SECRET`).
- `stripePriceMonthly`/`stripePriceYearly` — `defineString` params (Price
  ID-та от Stripe Dashboard, не са тайни, но не са hardcode-нати).
- `createCheckoutSession` (onCall) — създава Stripe Checkout Session,
  пази `firebaseUid` И като `client_reference_id` (за `checkout.session.completed`),
  И като `subscription_data.metadata.firebaseUid` (за по-късни
  `customer.subscription.*` събития, които нямат checkout контекст).
- `createBillingPortalSession` (onCall) — Stripe Customer Portal, за да
  може платен потребител сам да управлява/отказва абонамента си (изисква
  вече записан `stripeCustomerId` в `entitlements/{uid}`).
- `stripeWebhook` (onRequest, HTTP ендпойнт — Stripe вика директно, не
  през httpsCallable) — слуша `checkout.session.completed` (първо
  плащане → `entitlements/{uid}.premium = true`) и `customer.subscription.
  updated`/`.deleted` (подновяване/отказ → update спрямо `sub.status`).
  Използва `req.rawBody` (гарантирано от Firebase Functions framework-а)
  за проверка на `stripe-signature` хедъра — НЕ пипай body-parsing-а тук.
  URL за Stripe Dashboard → Webhooks: `https://europe-west1-iforgetbg.
  cloudfunctions.net/stripeWebhook`.

**Firestore rules** — `config/premium` (публично четим, `allow write:
if false`), `entitlements/{uid}` (четим само от собственика, `allow
write: if false` — САМО `stripeWebhook` през Admin SDK пише тук; иначе
всеки логнат клиент би могъл директно да си самозапише `premium:true`).

**Остава (действие от потребителя, когато реши да активира, не сега)**:
1. Създай Stripe акаунт (ако няма) + Products/Prices (Monthly €2.99,
   Yearly €19.99) в Stripe Dashboard.
2. `firebase functions:secrets:set STRIPE_SECRET_KEY` + `STRIPE_WEBHOOK_SECRET`.
3. При `firebase deploy` ще попита за `STRIPE_PRICE_MONTHLY`/`STRIPE_PRICE_YEARLY`
   (Price ID-тата от стъпка 1) — или зададени предварително през `.env.iforgetbg`.
4. Stripe Dashboard → Webhooks → добави ендпойнта отгоре, копирай
   webhook signing secret-а → `STRIPE_WEBHOOK_SECRET`.
5. `firebase deploy --only functions,firestore:rules`.
6. Тест с истинска (или Stripe test mode) карта.
7. Firestore Console → създай `config/premium` документ, `enabled: true` —
   това е реалното "активиране", без нищо друго.

### Двата бъга, които се виждат САМО в нативната обвивка (24.08.2026)

Намерени при първото истинско пускане на iPhone (TestFlight). И двата са
невидими в браузър — точно затова стояха толкова дълго.

**1. Линковете за поверителност/общи условия не правеха нищо.**
`<a href="privacy.html" target="_blank">` — относителен адрес. В нативната
обвивка се разрешава спрямо собствения origin на приложението
(`capacitor://localhost/...`). `target="_blank"` иска НОВ прозорец, а
WKWebView не може да отвори втори; Capacitor праща външните http(s)
адреси към системния браузър, но СОБСТВЕНИЯТ му origin не е "външен" —
значи никой не поема клика и той пропада тихо.
Решение: `LEGAL_BASE` — в нативното приложение адресът става абсолютен
(`https://iforget.eu/...`), тогава Capacitor го разпознава като външен и
го отваря навън. В браузър константата е празен низ, значи нищо не се
променя. `fixNativeLegalLinks()` пипа статичните връзки на екрана за
вход (пишат се преди скрипта); динамичните в профилното меню ползват
`LEGAL_BASE` направо при рисуване. Файловете СА в `www/` (виж
`FILES_TO_COPY`) — липсата им НЕ беше причината, не ги маха.

**2. При регистрация полето "Потвърди парола" оставаше зад клавиатурата.**
Формата за регистрация е с едно поле по-висока от тази за вход, затова
се проявяваше само там. Две причини, поправени заедно:
- `.auth-screen` беше `inset:0`, тоест `bottom:0` — мери се спрямо LAYOUT
  viewport-а. На това устройство `interactive-widget=resizes-content` не
  се поддържа (установено още при историята с `.bottombar` по-горе),
  значи layout viewport-ът НЕ се свива при клавиатура: екранът оставаше
  844px висок при 433px видими и долната му част беше физически под
  клавиатурата. Сега височината идва от `var(--app-height)` — същата,
  която `updateAppHeight()` вече смалява.
- Нямаше скролируем предшественик. Браузърът сам показва фокусираното
  поле, но само ако има какво да скролне. Оттам `overflow-y:auto`.
Центрирането мина от `justify-content:center` на `margin:auto 0` на
`.auth-card` — с включен overflow центрирането реже и двата края и
ГОРНИЯТ става недостижим (същият капан като при `.notes-inner`).

**Поуката (втори път същата):** Chromium не възпроизведе НИТО ЕДИН от
двата симптома — проверено с контролен опит за втория. Нативната обвивка
е друга среда и единственият надежден тест е реално устройство. Същото
важеше и за дългата история с клавиатурата в уеб версията.

### Подпис за Android release — ПОДГОТВЕН, НЕПРОВЕРЕН с реален build

`android/app/build.gradle` вече има `signingConfigs.release`, който чете
`android/keystore.properties` (в `.gitignore`, шаблон в
`keystore.properties.example`). Без него `./gradlew bundleRelease` прави
НЕподписан `.aab`, а Google Play отхвърля такъв веднага.

Блокът е УМИШЛЕНО по избор (`def hasKeystore = ...exists()`): на машина
без ключ проектът се отваря и компилира точно както преди, значи
`npm run open:android` и debug build-овете не са засегнати.

`storeFile` трябва да е АБСОЛЮТЕН път — относителен се смята спрямо
`android/app/`, не спрямо `android/`, което е лесен капан.

**✅ ПРОВЕРЕН с истински build (22.08.2026).** `./gradlew bundleRelease`
на Mac даде подписан `app-release.aab` (5.5 MB, `META-INF/IFORGET.RSA` в
корена на архива). Пълните стъпки за качване: `store/google-play.md`.

Два капана от първото пускане:
• **`jarsigner -verify` НЕ работи за `.aab`** — казва "no manifest." и за
  подписан файл, защото форматът не е jar. Проверявай подписа с
  `unzip -l ... | awk '$4 ~ /^META-INF\//'` (търси се `.RSA` в КОРЕНА;
  `base/root/META-INF/...` са вътрешни файлове на приложението и не са
  подпис) или направо с `./gradlew :app:signingReport` — там при успех
  пише `Config: release` вместо `Config: null`.
• `keystore.properties` върви в `android/`, НЕ в `android/app/` —
  `rootProject.file()` сочи към `android/`.

СА В REPO-ТО и се генерират с два скрипта, не на ръка:

```
node store/generate.js       # 5 снимки (1290×2796) + банер (1024×500)
node store/check-lengths.js  # текстовете спрямо лимитите на магазините
```

- **`generate.js`** рендира от ИСТИНСКИЯ `index.html` през Playwright, не
  от макет — снимките винаги съвпадат с реалното приложение. Firebase е
  подменен с `fbstub.js` (фиктивен "влязъл" потребител + подготвени
  бележки), значи без акаунт и без мрежа. Демо съдържанието е нарочно
  БЕЗ месечен цикъл.
  Три капана, хванати при писането — не ги "поправяй" обратно:
  • **`LANG=bg_BG.UTF-8` в `chromium.launch({env})` е задължителен.**
    Родните `<input type="date"/"time">` се рисуват по локала на
    браузърния ПРОЦЕС, не по `locale` на контекста/страницата — без него
    датата излиза `08/21/2026 06:30 PM` вместо `21.08.2026 г. 18:30`.
    Само `args:['--lang=bg-BG']` НЕ стига (проверено).
  • **Шрифтовете се сервират от `store/fonts/`** (Cormorant Garamond +
    DM Sans, с кирилица, OFL, ~208 KB), защото Chromium тук не стига до
    `fonts.googleapis.com` — иначе снимките излизат с резервен системен
    шрифт. `page.route()` пренасочва заявките натам. Ако шрифт в
    `index.html` се смени, виж `store/fonts/README.md` как се обновяват.
  • **Формата за напомняне НЕ се отваря с `renderCtxMenuReminder()`
    веднага след `openCtxMenu()`** — менюто още се позиционира и остава
    на главния списък с бутони. Кликва се значката на напомнянето
    (`data-action="reminder-open"`), тоест същинският път на потребителя.
- **`store-listing-texts.md`** — описания на бг+en. Съзнателно БЕЗ
  месечния цикъл (функцията остава, само не се рекламира) и БЕЗ обещание
  за дълготрайно съхранение (виж `archiveOldCompleted()` — приключените
  се чистят след 30 дни, обещание за архив би било некоректно). Абзаците
  са на ЕДИН ред — магазините пазят прекъсванията на редовете буквално.
  Съдържа и списък какво се качва къде + "провери преди да качиш".
- **`pages.yml` маха `store/` преди Pages deploy**, както `scripts/` —
  4 MB работни файлове нямат работа публично на `iforget.eu`.

**Описанието обещава напомняния — и вече е проверено, че звънят**
(Samsung Galaxy A17 / Android 16, 22.08.2026; виж раздела за напомнянията
по-горе). Дотогава тук стоеше предупреждение за разминаване, защото
`@capacitor/local-notifications` не беше закачен за нативните проекти.
Закача се от `npx cap sync`, който `npm run open:android`/`open:ios`
пускат вътре в себе си — затова нативният проект НЕ се отваря директно.

## Планирани задачи (за после, не сега)
- **Споделени бележки/тагове между няколко акаунта** (напр. споделен
  списък за пазаруване или общи задачи, редактируем от повече от един
  човек). В момента архитектурата е строго лична — `users/{uid}` документ
  с бележки, security rules позволяват четене/писане само на собственика;
  никой друг акаунт не вижда чужди данни. Реалистичен обхват (без нужда от
  Cloud Functions/Blaze):
  - Нова колекция `sharedLists/{listId}` с масив `memberEmails` — security
    rules позволяват четене/писане на всеки, чийто вход-имейл присъства в
    масива (Firestore проверява директно от auth токена, без сървър).
  - Покана с имейл адрес (просто добавяне в `memberEmails`).
  - Синхронизация при обновяване на екрана (както сега), или с realtime
    listener (`onSnapshot()` вместо еднократен `.get()`) за по-плавно
    виждане на промените на другите почти веднага — умерена промяна в кода.
  - **НЕ** включва истинско едновременно писане буква по буква (като Google
    Docs) — това изисква съвсем различна технология (operational
    transforms/CRDT) и е отделна, много по-голяма задача, извън обхвата тук.
  Съзнателно отложено — не блокира нищо в сегашното приложение.

## Преди масово пускане — какво е готово vs. какво остава за потребителя

Направено в кода (не изисква нищо допълнително от потребителя):
- Потвърждение на имейл при регистрация (банер + resend).
- Политика за поверителност / Общи условия (`privacy.html`/`terms.html`),
  свързани от входния екран и профила.
- Бутон "Обратна връзка" (mailto) в профила.

Изисква действие от потребителя извън repo-то (не мога да го направя вместо
нея — няма Firebase CLI/Console API достъп в тази среда):

1. ~~**Firebase план → Blaze**~~ — **НАПРАВЕНО** (потвърдено от потребителя).
   Отключва Cloud Functions/Storage за в бъдеще (снимки, брандиран линк за
   забравена парола).
2. ~~**Публикуване на финалните Firestore security rules**~~ — **НАПРАВЕНО**
   (потвърдено от потребителя, пуснато в Firebase Console → Firestore →
   Rules → Publish). Черновата остава по-долу само за референция, ако
   правилата трябва да се редактират пак в бъдеще (напр. нова колекция за
   снимки/Storage rules).
3. **App Check / reCAPTCHA** (по избор, но препоръчително при масово
   пускане) — Firebase Console → App Check → Web apps → reCAPTCHA v3,
   за защита на формата за регистрация от ботове.
4. **Преглед на превода** на ru/de/es от носител на съответния език —
   преводите в момента са направени от мен (Клод), с грижа, но непроверени
   от носител.
5. **Преглед на privacy.html/terms.html от юрист** (по избор, но
   препоръчително) — текстовете са добросъвестна чернова, не юридическа
   консултация.

### Чернова на Firestore security rules (за т. 2 по-горе)

```
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    match /users/{userId} {
      // Собственикът чете/пише само своя документ.
      allow read, write: if request.auth != null && request.auth.uid == userId;
      // Admin акаунтът (виж SATORI_EMAIL в index.html) чете цялата колекция
      // само за статистика — НЕ може да пише в чужди документи.
      allow read: if request.auth != null
                   && request.auth.token.email == 'neshovska@yahoo.com';
    }
  }
}
```

Ако текущите ѝ правила вече правят точно това, тази стъпка е просто
потвърждение, не промяна.
